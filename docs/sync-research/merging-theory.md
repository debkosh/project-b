# Merge theory for browser sync: strategies, clocks, deletes, order, trees, identity, UX

Scope: published theory, guidelines and known pitfalls. What specific browsers do is covered elsewhere. The owner's model under review: every item is `{guid, type, timestamp, deleted, data}`, newest timestamp wins per guid, parent and order live inside `data`, devices write only their own files to dumb storage with no server.

In the literature's terms, that model is a map from guid to a last-writer-wins (LWW) register, where each device publishes its whole state and every reader merges all files. That is a state-based CRDT ([Shapiro et al. 2011](https://hal.sorbonne-universite.fr/inria-00609399v1)). It converges, which is the easy part. The real questions are what it loses, and whether the users will notice.

## 1. The menu of strategies

**Last writer wins (LWW register).** Each write carries a timestamp and the highest one wins. It is the simplest CRDT and the one Figma uses per property ([Figma, Wallace](https://www.figma.com/blog/how-figmas-multiplayer-technology-works/)). Weidner's survey describes it the same way, and recommends logical timestamps over wall-clock ones because clock skew can make a local overwrite fail ([Weidner, CRDT survey part 2](https://mattweidner.com/2023/09/26/crdt-survey-2.html)). Its known cost is that it never keeps both sides of a concurrent update. Jepsen measured Riak losing about 72% of acknowledged writes under LWW in a healthy cluster ([Kingsbury, Jepsen: Riak](https://aphyr.com/posts/285-jepsen-riak)), and Cassandra losing about 28% of concurrent writes to the same cell ([Kingsbury, Jepsen: Cassandra](https://aphyr.com/posts/294-jepsen-cassandra)). Riak's own docs say LWW "will necessarily drop some writes in the case of concurrent updates" ([Riak conflict resolution](https://docs.riak.com/riak/kv/2.1.4/developing/usage/conflict-resolution/)). LWW is recommended when concurrent edits to the same value are rare, and when losing one of them is acceptable.

**Multi-value register (keep both, siblings).** Concurrent writes are all kept, and the reader or the user picks. Weidner defines it as "the set of all values that have not yet been overwritten", and suggests showing one default value while keeping the others ([Weidner, part 2](https://mattweidner.com/2023/09/26/crdt-survey-2.html)). Amazon's Dynamo returned all concurrent versions to the application for reconciliation, with the shopping cart as the example ([DeCandia et al., Dynamo, SOSP 2007](https://www.allthingsdistributed.com/files/amazon-dynamo-sosp2007.pdf)). Riak made siblings the default for new bucket types in 2.0 ([Riak docs](https://docs.riak.com/riak/kv/2.1.4/developing/usage/conflict-resolution/)). Kingsbury's advice after the Riak test was "Enable allow-mult. Use CRDTs" ([Jepsen: Riak](https://aphyr.com/posts/285-jepsen-riak)). You can only detect "concurrent" with causal metadata such as version vectors (section 2). It is recommended where a lost write is costly, for example a changed password.

**Per-field merge (map of registers).** Each field is its own register, so concurrent edits to different fields both survive. Weidner calls this an "object" or "map-like object" whose components "don't affect each others' operations or states", and advises matching write granularity to the properties users edit independently ([Weidner, part 2](https://mattweidner.com/2023/09/26/crdt-survey-2.html)). Figma is LWW per property, not per object ([Figma](https://www.figma.com/blog/how-figmas-multiplayer-technology-works/)). Apple's Core Data offers the same choice as a merge policy, property-level "object trumps" versus whole-object overwrite ([NSMergePolicy](https://developer.apple.com/documentation/coredata/nsmergepolicy)). This is the cheapest upgrade over whole-item LWW.

**Three-way merge against a common base.** Compare both sides with the last state they agreed on. A field changed on one side only is taken from that side, and a field changed on both is a true conflict. Dropbox's rewritten sync engine keeps three trees (remote, local, synced) and treats the synced tree as the merge base, because without it you cannot tell an add on one side from a delete on the other ([Dropbox, Testing sync](https://dropbox.tech/infrastructure/-testing-our-new-sync-engine), [Rewriting the heart of our sync engine](https://dropbox.tech/infrastructure/rewriting-the-heart-of-our-sync-engine)). The formal properties and surprises of diff3 are worked out by [Khanna, Kunal and Pierce](https://www.cis.upenn.edu/~bcpierce/papers/diff3-short.pdf). The Harmony project applied schema-driven state-based merge to tree-structured data, and used it to synchronize browser bookmark files across machines ([Foster et al., Exploiting Schemas in Data Synchronization](https://repository.upenn.edu/cis_papers/344), [Pierce, Harmony: The Art of Reconciliation](https://springerlink.bibliotecabuap.elogim.com/content/pdf/10.1007/11580850_1.pdf)). It is recommended when each device can cheaply remember the last synced state. A device writing its own file can do this.

**Operational transformation (OT).** Operations are rewritten against concurrent operations. It comes from [Ellis and Gibbs 1989](https://dl.acm.org/doi/10.1145/67544.66963), and intention preservation was formalised by [Sun et al. 1998](https://dl.acm.org/doi/10.1145/274444.274447). Figma rejected it as "unnecessarily complex for our problem space" ([Figma](https://www.figma.com/blog/how-figmas-multiplayer-technology-works/)). Joseph Gentle, who built Google Wave's OT, says OT's "one advantage is that it fits well in centralized software" ([Gentle, I was wrong. CRDTs are the future](https://josephg.com/blog/crdts-are-the-future/)). It needs a central sequencer in practice, so it does not fit dumb storage. It is not recommended here.

**CRDTs, state-based versus op-based.** State-based CRDTs ship whole state and merge with a join. Op-based CRDTs ship operations, which must be delivered exactly once in causal order. Both are defined in [Shapiro et al. 2011](https://hal.sorbonne-universite.fr/inria-00609399v1) and catalogued in [Shapiro et al., A comprehensive study of CRDTs](https://inria.hal.science/inria-00555588). Delta-state CRDTs ship only the changed part of a state-based CRDT ([Almeida, Shoker, Baquero, Delta State Replicated Data Types](https://arxiv.org/abs/1603.01529)). Sypytkowski's introduction walks through LWW registers, vector clocks and tombstones in the state-based style ([Sypytkowski, An introduction to state-based CRDTs](https://www.bartoszsypytkowski.com/the-state-of-a-state-based-crdts/)). Per-device files on dumb storage are naturally state-based or delta-state, because there is no reliable channel for exactly-once operation delivery. Kleppmann's warning applies: "CRDTs are easy to implement badly", and many published algorithms have anomalies ([Kleppmann, CRDTs: The Hard Parts](https://martin.kleppmann.com/2020/07/06/crdt-hard-parts-hydra.html)). Gentle's later work shows performance is now solvable ([Gentle, 5000x faster CRDTs](https://josephg.com/blog/crdts-go-brrr/), [Gentle and Kleppmann, Eg-walker](https://arxiv.org/abs/2409.14252)), but that work is about text, which browser sync does not need.

**Server reconciliation and rebase.** A server fixes the total order, and clients undo their pending local operations, apply the server's operations, then redo their own. Weidner argues that "CRDTs and OT are merely optimizations over server reconciliation, which is straightforward and completely flexible" ([Weidner, Architectures for Central Server Collaboration](https://mattweidner.com/2024/06/04/server-architectures.html)). Bayou is the classic version, with per-write dependency checks and merge procedures, and rollback and redo in a global order ([Terry et al., Bayou, SOSP 1995](https://www.cs.princeton.edu/courses/archive/fall15/cos518/papers/bayou.pdf)). It needs a single authority, so it does not apply without a server. A lighter cousin that does apply is to run the merge, check invariants, and repair the result deterministically (section 5).

**Ask the human.** Apple's guide lists three strategies (merge, pick one by a pertinent factor such as the latest date, or let the user choose), and says "Generally, you should try to resolve the conflict without involving the user" ([Apple, Resolving Document Version Conflicts](https://developer.apple.com/library/archive/documentation/DataManagement/Conceptual/DocumentBasedAppPGiOS/ResolveVersionConflicts/ResolveVersionConflicts.html)). File-sync products fall back to keep-both copies, for example Dropbox's "conflicted copy" ([Dropbox help](https://help.dropbox.com/organize/conflicted-copy)). Section 7 covers when this is worth it.

The survey literature behind all of this is [Saito and Shapiro, Optimistic Replication, ACM Computing Surveys 2005](https://www.lip6.fr/Marc.Shapiro/papers/Optimistic_Replication_Computing_Surveys_2005-03_cameraready.pdf). Weidner's framing helps when choosing: first decide the semantics (what the state should be after concurrent edits), then choose the algorithm that computes it ([Weidner, part 1](https://mattweidner.com/2023/09/26/crdt-survey-1.html)).

## 2. Clocks

**Wall clocks are unsafe as the only order.** Kingsbury: "Timestamps, as implemented in Riak, Cassandra, et al, are fundamentally unsafe ordering constructs", and "NTP does not solve it for you". Clocks step backwards through NTP corrections, virtualization and leap seconds. A process can write, then write again with a smaller timestamp, and lose its own second write ([Kingsbury, The trouble with timestamps](https://aphyr.com/posts/299-the-trouble-with-timestamps)). Justin Sheehy makes the same case in [There is No Now (ACM Queue)](https://queue.acm.org/detail.cfm?id=2745385). Riak's docs say timestamps "always bear the risk of data loss" ([Riak docs](https://docs.riak.com/riak/kv/2.1.4/developing/usage/conflict-resolution/)). Consumer devices are worse than servers here: a phone with the wrong time set, or with a dead clock battery, will write timestamps from the past or the future.

**The skewed-future write.** One device with its clock set ahead wins every conflict until real time catches up. Its delete, with a far-future timestamp, silently discards every later write. Kingsbury calls these "doomstones" ([The trouble with timestamps](https://aphyr.com/posts/299-the-trouble-with-timestamps)).

**Same-millisecond ties.** Cassandra breaks equal timestamps by picking the lexicographically bigger value, which mixed fields from different writes in Jepsen's test, about 1 row in 200 ([Jepsen: Cassandra](https://aphyr.com/posts/294-jepsen-cassandra)). Any LWW needs a deterministic tie-breaker on the whole item, such as a device id.

**Lamport clocks.** A counter that each node advances past any value it has seen gives an order consistent with causality ([Lamport 1978](https://lamport.azurewebsites.net/pubs/time-clocks.pdf)). A write made after reading another write always wins over it. It cannot tell "concurrent" from "after".

**Hybrid logical clocks (HLC).** Each timestamp is a pair: the max physical time seen, plus a counter. It captures causality like a Lamport clock, stays close to wall-clock time, and fits in 64 bits ([Kulkarni et al., Logical Physical Clocks, OPODIS 2014](https://www.cse.buffalo.edu//~demirbas/publications/hlc.pdf)). Its rule is that a node never issues a timestamp lower than any it has seen, so a write made after reading another always sorts after it, whatever the local clock says. It can still be dragged forward by a device with a future clock, so implementations bound the accepted drift.

**Version vectors and dotted version vectors.** A vector of per-replica counters detects concurrency exactly ([Parker et al. 1983](https://doi.org/10.1109/TSE.1983.236733), [Wikipedia: Version vector](https://en.wikipedia.org/wiki/Version_vector)). Riak found that plain vectors cause "sibling explosion", and moved to dotted version vectors, where each value carries the one event (the dot) that created it, so siblings grow only with real concurrency ([Riak, Vector clocks revisited part 2](https://riak.com/posts/technical/vector-clocks-revisited-part-2-dotted-version-vectors/), [Preguiça et al., Dotted Version Vectors](https://arxiv.org/abs/1011.5808), [Riak causal context](https://docs.riak.com/riak/kv/2.2.3/learn/concepts/causal-context)). You need these only if you want to keep both values (a multi-value register). For pure LWW, an HLC is enough.

## 3. Deletes

**Tombstones are mandatory.** If a deleted item just disappears from a device's file, another device that still has it will copy it back. Every state-based design keeps a deletion marker. Demers et al. called these "death certificates" ([Demers et al., Epidemic Algorithms, 1987](https://ftp.mirrorservice.org/sites/www.bitsavers.org/pdf/xerox/parc/techReports/CSL-89-1_Epidemic_Algorithms_for_Replicated_Database_Maintenance.pdf)). Sypytkowski notes that in a two-phase set a removed element "will stay in tombstone forever", and the removed set "can grow infinitely" ([Sypytkowski](https://www.bartoszsypytkowski.com/the-state-of-a-state-based-crdts/)). The owner's `deleted` flag is a tombstone, which is correct.

**Delete versus concurrent edit.** Under LWW on the whole item, whichever is newer wins. A later edit brings the item back (edit-wins), and a later delete wins over an earlier edit. The set literature names the two policies add-wins and remove-wins. Weidner prefers add-wins, saying "I also do not know of an example app where I prefer the remove-wins set's semantics" ([Weidner, part 2](https://mattweidner.com/2023/09/26/crdt-survey-2.html)). The observed-remove set is the standard add-wins construction ([Bieniusa et al., An optimized conflict-free replicated set](https://arxiv.org/abs/1210.3368)). The classic failure in the other direction is Dynamo, where deleted shopping-cart items could resurface after a merge ([Dynamo paper, section 4.4](https://www.allthingsdistributed.com/files/amazon-dynamo-sosp2007.pdf)). The trap in plain LWW: an edit on a device that never saw the delete, but carries a newer timestamp, resurrects the item. With an HLC, an edit made after seeing the delete is causally later, and one made without seeing it is concurrent, so the timestamp alone cannot tell "the user restored it on purpose" from "a stale device touched it".

**Tombstone garbage collection and the stale device.** Dropping a tombstone is safe only once every replica has seen it, which the literature calls causal stability ([Baquero, Almeida, Shoker, Making Operation-based CRDTs Operation-based](https://repositorium.sdum.uminho.pt/bitstream/1822/37695/2/1867.pdf)). In practice, systems use a time horizon. Cassandra keeps tombstones for `gc_grace_seconds`, ten days by default. A node that is down longer than that comes back with the old row and resurrects it as a "zombie" ([Apache Cassandra, Tombstones](https://cassandra.apache.org/doc/latest/cassandra/managing/operating/compaction/tombstones.html)). Demers' "dormant death certificates" keep old tombstones at a few sites, and reactivate them when an obsolete item reappears ([Demers et al.](https://ftp.mirrorservice.org/sites/www.bitsavers.org/pdf/xerox/parc/techReports/CSL-89-1_Epidemic_Algorithms_for_Replicated_Database_Maintenance.pdf)). ScyllaDB moved to repair-based tombstone GC, so tombstones are dropped only after all replicas are known to have them ([ScyllaDB](https://resources.scylladb.com/blog/preventing-data-resurrection-with-repair-based-tombstone-garbage-collection)). The lesson for per-device files: a device that has been away longer than the tombstone horizon must not push its old state as if it were new. It must first adopt the others' state (a reset), then re-add only what it changed locally since its last sync.

**Recursive deletes.** Weidner advises against deleting a subtree node by node ("don't actually loop over the subtree deleting nodes"). Delete or archive only the top node, and let the children be hidden because their ancestor is gone ([Weidner, part 2](https://mattweidner.com/2023/09/26/crdt-survey-2.html)). That way a concurrent add into the subtree is not silently lost, and undo is a single flip.

## 4. Ordered lists

**Do not store order as an array inside the parent.** An array of child ids in the parent's `data` makes every insert and every reorder a write to the parent. Under LWW, two devices that each add a bookmark to the same folder lose one of the adds. The CRDT literature replaces indices with stable ids and per-element positions ([Weidner, part 2, Unique IDs and Lists](https://mattweidner.com/2023/09/26/crdt-survey-2.html)).

**Fractional indexing.** Each child stores a position key that sorts between its neighbours. The name was coined by Figma ([Wallace, Realtime editing of ordered sequences](https://www.figma.com/blog/realtime-editing-of-ordered-sequences/)). Figma stores parent and position together as one property, so a move is a single LWW write ([Figma multiplayer](https://www.figma.com/blog/how-figmas-multiplayer-technology-works/)). It has three known problems. Two devices can generate the same key, which is fixed by appending a device id ([Sypytkowski, Scaling Fractional Indexes](https://www.bartoszsypytkowski.com/scaling-fractional-indexes/)). Keys grow as you keep inserting in the same gap ([same post](https://www.bartoszsypytkowski.com/scaling-fractional-indexes/)). Concurrent runs of inserts at the same spot can interleave ([vlcn / cr-sqlite, Fractional Indexing](https://vlcn.io/blog/fractional-indexing)). Wallace accepted interleaving because Figma "didn't need to avoid interleaving" ([Wallace](https://www.figma.com/blog/realtime-editing-of-ordered-sequences/)).

**Interleaving and list CRDTs.** Interleaving is the main anomaly of list CRDTs ([Kleppmann et al., Interleaving anomalies, PaPoC 2019](https://martin.kleppmann.com/papers/interleaving-papoc19.pdf)). Fugue and FugueMax minimise it, and FugueMax is proven maximally non-interleaving ([Weidner and Kleppmann, The Art of the Fugue](https://arxiv.org/abs/2305.00583), [Kleppmann's post](https://martin.kleppmann.com/2025/11/01/fugue-minimizing-interleaving.html)). Weidner's position-strings give fractional-index-like keys without interleaving, at 10 to 100 characters a key ([Weidner, Position Strings](https://mattweidner.com/2023/04/13/position-strings.html)). Interleaving matters for typed text. For bookmarks it shows up only when two devices each add several items to the same gap while offline, and even then the result is a valid order.

**Concurrent reorders.** If a move is a delete plus a re-insert, two concurrent moves of the same item produce two copies ([Sypytkowski, Replacing Yjs move feature](https://www.bartoszsypytkowski.com/replacing-yjs-move-feature/), [Kleppmann, Moving Elements in List CRDTs](https://www.cl.cam.ac.uk/research/dtg/www/files/publications/public/mk428/list-move-papoc20.pdf)). The fix both give is to keep the item's identity and make its position a single LWW register, so one move wins and the item appears exactly once. Kleppmann notes that moving a range of items is still an open problem ([PaPoC 2020](https://www.cl.cam.ac.uk/research/dtg/www/files/publications/public/mk428/list-move-papoc20.pdf)).

## 5. Trees

**Cycles.** With a parent pointer per node, device A moves folder X into Y while device B moves Y into X. Both writes are valid alone. Merged, X and Y form a cycle detached from the root ([Weidner, part 2, Forests and Trees](https://mattweidner.com/2023/09/26/crdt-survey-2.html), [Kleppmann et al., A highly-available move operation for replicated trees](https://martin.kleppmann.com/papers/move-op.pdf)).

**The known approaches.**
- *Server rejects the move.* Figma's server refuses any update that would create a cycle, and clients briefly detach the looping objects until it answers ([Figma](https://www.figma.com/blog/how-figmas-multiplayer-technology-works/)). This needs a server.
- *Undo-do-redo over a timestamped log.* Kleppmann et al. order all moves by Lamport timestamp. A move that would create a cycle at its place in that order is ignored, and a late-arriving move is applied by undoing the later ones, applying it, and redoing them. They proved this correct in Isabelle/HOL, and delete is a move into a trash node ([Kleppmann et al., IEEE TPDS 2022](https://martin.kleppmann.com/papers/move-op.pdf)). It needs each device to keep the move log, not just the latest state.
- *Repair at read time.* Merge the parent registers, then deterministically break any cycle, for example by ignoring the newest parent write on the cycle, or by moving the cycle under a recovery folder. Weidner lists erroring, a "time-out" zone, server rejection and topological sorting as the options ([Weidner, part 2](https://mattweidner.com/2023/09/26/crdt-survey-2.html)). This is the only option that fits LWW state with no server and no log. Its weakness is that "ignore the newest parent write" needs the node's previous parent, which a single LWW register does not keep, so the practical fallback is a fixed recovery location.

**Orphans.** A child whose parent is deleted or missing (deleted, or not yet arrived from the other device's file) needs a rule. The options are to hide it with the deleted parent (Weidner's archive-the-top-node approach), to show it in a fallback location, or to un-delete the parent (add-wins applied to the tree). The move-op paper's trash node is the first option made explicit ([Kleppmann et al.](https://martin.kleppmann.com/papers/move-op.pdf)). Harmony's bookmark work deals with the same problem through schema-aware merging ([Foster et al.](https://repository.upenn.edu/cis_papers/344)). Whatever the rule, it has to be a pure function of the merged state, so every device shows the same tree.

## 6. Identity and duplicate creation

**Random ids for user-created items.** Figma gives each client a unique id and embeds it in every object id, so creation works offline without collisions ([Figma](https://www.figma.com/blog/how-figmas-multiplayer-technology-works/)). Weidner's rule is to refer to content by an immutable unique id, never by a mutable position ([Weidner, part 2, Unique IDs](https://mattweidner.com/2023/09/26/crdt-survey-2.html)).

**"The same" thing created twice.** If two devices each create the Bookmarks Bar, the default search engine setting, or the same saved password before they first sync, random ids give two items, which is a duplicate. CRDT libraries assume shared objects are created once and then forked. The Automerge guides start peers from one common base document, not from two documents built independently ([Automerge R docs, CRDT concepts](https://cran.r-project.org/web/packages/automerge/vignettes/crdt-concepts.html)). Weidner's "map-like object", where "each key implicitly always exists", is the fix: a well-known key, not a created object ([Weidner, part 2](https://mattweidner.com/2023/09/26/crdt-survey-2.html)). For singletons this means a fixed, deterministic guid (for example `toolbar` or `setting:homepage`), the same on every device.

**Content-addressed ids** suit immutable records. A history visit (url, time, device) never changes, so a hash of it is a safe id, and the same visit imported twice merges with itself. They do not suit editable items, because editing would change the id, and users keep intentional duplicates (the same URL in two folders).

**Natural-key de-duplication.** For items that have a natural key but random ids, such as a password's (origin, username) pair, a first-sync merge can match on the key and keep one guid. This is application logic, not a CRDT property. Dropbox's three-tree work shows why it should run against a merge base: without one, "added here" and "deleted there" look the same ([Dropbox, Testing sync](https://dropbox.tech/infrastructure/-testing-our-new-sync-engine)).

## 7. Intent and user-facing guidance

**When silent auto-merge is fine.** The local-first essay reports that in their prototypes "users surprisingly rarely encounter conflicts", and that when the same property of the same object is changed concurrently, "it is often arbitrary how they are resolved and satisfactory either way" ([Kleppmann et al., Local-first software, Onward! 2019](https://www.inkandswitch.com/essay/local-first/)). Apple says to pick the latest version only "if your application doesn't suffer any loss of data as a result" ([Apple guide](https://developer.apple.com/library/archive/documentation/DataManagement/Conceptual/DocumentBasedAppPGiOS/ResolveVersionConflicts/ResolveVersionConflicts.html)). Read together: auto-merge silently when the losing value is cheap to recreate, or obviously superseded.

**When to surface it.** Surface a conflict when the loser is not easy to recreate and the user would not notice it is gone. Apple says that if user resolution is needed, the app "should discreetly inform the user about the version conflict and expose a button or other control that initiates the resolution procedure", and `NSFileVersion` gives modification dates and the saving computer's name to show ([Apple guide](https://developer.apple.com/library/archive/documentation/DataManagement/Conceptual/DocumentBasedAppPGiOS/ResolveVersionConflicts/ResolveVersionConflicts.html), [NSFileVersion](https://developer.apple.com/documentation/foundation/nsfileversion)). The local-first essay criticises apps that offer "nothing to support the user in resolving the situation" ([Local-first](https://www.inkandswitch.com/essay/local-first/)).

**Keep both rather than lose.** Dropbox names the loser with the editor, "conflicted copy" and the date ([Dropbox](https://help.dropbox.com/organize/conflicted-copy)). OneDrive offers "merge changes or keep both copies", and keep-both appends the computer name ([OneDrive settings, third-party description](https://sharepointmaven.com/how-onedrive-sync-resolves-sync-conflicts/)). Microsoft later announced it would remove the fork option for Office files in favour of merging inside Office ([MC660614](https://app.cloudscout.one/evergreen-item/MC660614)). These are file-level fallbacks. For structured items, keeping the losing value in a recoverable place does the same job without cluttering the user's data.

**Nielsen Norman Group** has no article on sync conflicts specifically, as far as I found. Its general heuristic, keep users informed about what is going on, applies to sync status ([NN/g, Visibility of System Status](https://www.nngroup.com/articles/visibility-system-status/)). A List Apart's offline-first article suggests a simple interface that shows the differences and lets the user pick the winning version ([Feyerke, Designing Offline-First Web Apps](https://alistapart.com/article/offline-first/)).

## Guidelines we can adopt

1. **Build the timestamp as a hybrid logical clock, with the device id as the tie-breaker.** Store `(max(local wall clock, highest timestamp seen in any file read), counter, device id)`. A device never writes a timestamp lower than one it has read, so an edit made after seeing another always wins, whatever the local clock says. Order ties by device id, never by value. Sources: [Kulkarni et al.](https://www.cse.buffalo.edu//~demirbas/publications/hlc.pdf), [Lamport](https://lamport.azurewebsites.net/pubs/time-clocks.pdf), [Jepsen: Cassandra ties](https://aphyr.com/posts/294-jepsen-cassandra), [Weidner on logical timestamps](https://mattweidner.com/2023/09/26/crdt-survey-2.html).

2. **Cap future timestamps.** When reading a file, do not let the clock jump to a timestamp far ahead of local wall time (for example more than a day). Clamp or flag it, so one device with a wrong clock cannot win every conflict or plant a "doomstone". Source: [Kingsbury, The trouble with timestamps](https://aphyr.com/posts/299-the-trouble-with-timestamps).

3. **Make the LWW unit the field group users edit independently, not the whole item.** For bookmarks that is three registers: title, url, and (parent, position) together, as Figma does. Then a rename on one device and a move on another both survive. Each register carries its own timestamp inside `data`, so the envelope stays as the owner designed it. Sources: [Weidner, objects and map-like objects](https://mattweidner.com/2023/09/26/crdt-survey-2.html), [Figma](https://www.figma.com/blog/how-figmas-multiplayer-technology-works/), [Apple NSMergePolicy](https://developer.apple.com/documentation/coredata/nsmergepolicy).

4. **Keep order on the child, as a fractional index with the device id appended. Never as a child list in the parent.** Adds to the same folder from two devices then both survive, a reorder is one write to one item, and an item can never appear twice. Accept interleaving for bookmarks. Sources: [Wallace](https://www.figma.com/blog/realtime-editing-of-ordered-sequences/), [Sypytkowski, Scaling Fractional Indexes](https://www.bartoszsypytkowski.com/scaling-fractional-indexes/), [Sypytkowski, Replacing Yjs move](https://www.bartoszsypytkowski.com/replacing-yjs-move-feature/), [Kleppmann, list move](https://www.cl.cam.ac.uk/research/dtg/www/files/publications/public/mk428/list-move-papoc20.pdf).

5. **Compute the tree as a pure function of the merged state, with fixed repair rules.** A node whose parent chain hits a cycle, or a missing parent, goes to one fixed recovery location (for example "Other bookmarks"), the same on every device. Do not write the repair back unless the user then edits the item, so two devices do not fight over the repair. Sources: [Weidner, forests and trees](https://mattweidner.com/2023/09/26/crdt-survey-2.html), [Kleppmann et al., move-op](https://martin.kleppmann.com/papers/move-op.pdf).

6. **Delete a folder by tombstoning the folder only.** Its children become hidden because their ancestor is deleted. Do not write tombstones for the whole subtree. A bookmark another device added into it concurrently is then recoverable, and undo is one write. Source: [Weidner, part 2](https://mattweidner.com/2023/09/26/crdt-survey-2.html).

7. **Delete versus edit: newest timestamp wins, with the HLC making "newest" mean "seen later".** This is edit-wins when the edit came after the delete was seen, which matches the add-wins recommendation. Source: [Weidner, add-wins](https://mattweidner.com/2023/09/26/crdt-survey-2.html), [Bieniusa et al.](https://arxiv.org/abs/1210.3368).

8. **Keep tombstones for a fixed horizon (for example 90 days), and make a device that has been away longer than that reset before it writes.** Such a device takes everyone else's state as the truth, then re-applies only the local changes it made since its last sync, with fresh timestamps. Without this, a laptop left in a drawer resurrects deleted bookmarks. Sources: [Cassandra gc_grace and zombies](https://cassandra.apache.org/doc/latest/cassandra/managing/operating/compaction/tombstones.html), [Demers et al.](https://ftp.mirrorservice.org/sites/www.bitsavers.org/pdf/xerox/parc/techReports/CSL-89-1_Epidemic_Algorithms_for_Replicated_Database_Maintenance.pdf), [Baquero et al., causal stability](https://repositorium.sdum.uminho.pt/bitstream/1822/37695/2/1867.pdf).

9. **Each device remembers its last synced state (a merge base).** It costs one more copy on the device. It lets a device tell "I changed this" from "they changed this", which is needed for rule 8 and for the passwords rule below. Source: [Dropbox, three trees](https://dropbox.tech/infrastructure/-testing-our-new-sync-engine).

10. **Give singletons fixed guids.** The roots (toolbar, other, mobile), each setting (`setting:<name>`) and any per-profile record get the same deterministic guid on every device, so first sync merges them, not duplicates them. A setting keyed by its name is also, for free, a per-field LWW register. Sources: [Weidner, map-like object](https://mattweidner.com/2023/09/26/crdt-survey-2.html), [Automerge, shared base](https://cran.r-project.org/web/packages/automerge/vignettes/crdt-concepts.html).

11. **Give history visits content-derived guids.** A hash of (url, visit time, device) makes visits immutable, and re-imports idempotent. Visits are never edited, only added or tombstoned. Source: [Weidner, unique IDs](https://mattweidner.com/2023/09/26/crdt-survey-2.html).

12. **De-duplicate passwords on (origin, username) at merge, and never drop a losing password value silently.** When two devices changed the same login concurrently (both changed it since the merge base), keep the newest as current, and keep the other in the item's history so the user can get it back. This is the one type where a lost write locks the user out of a site. Sources: [Apple, latest only if no data loss](https://developer.apple.com/library/archive/documentation/DataManagement/Conceptual/DocumentBasedAppPGiOS/ResolveVersionConflicts/ResolveVersionConflicts.html), [Riak and Dynamo on keeping siblings](https://docs.riak.com/riak/kv/2.1.4/developing/usage/conflict-resolution/), [Jepsen: Riak](https://aphyr.com/posts/285-jepsen-riak).

13. **Surface conflicts quietly, and only for passwords.** Show a discreet "this login was changed on two devices" note with both dates and device names, with a control to choose, as Apple's guide describes. Everything else resolves silently. Sources: [Apple guide](https://developer.apple.com/library/archive/documentation/DataManagement/Conceptual/DocumentBasedAppPGiOS/ResolveVersionConflicts/ResolveVersionConflicts.html), [Local-first, arbitrary is usually fine](https://www.inkandswitch.com/essay/local-first/).

### Where the owner's model is enough as is

- **Open tabs.** Each device's tabs are written only by that device, so there are no concurrent writers and nothing to merge. The other devices only read them.
- **Settings**, once each setting is its own guid (rule 10). Newest wins per setting is what users expect, and a lost concurrent change is cheap to redo ([Local-first](https://www.inkandswitch.com/essay/local-first/)).
- **History visits**, with content-derived guids (rule 11). They are add-only, and LWW only ever decides a delete.
- **The envelope itself.** `{guid, type, timestamp, deleted, data}` with newest-wins per guid is a correct state-based CRDT. It converges whatever order files are read in, and the per-device single-writer files avoid write-write conflicts on storage ([Shapiro et al.](https://hal.sorbonne-universite.fr/inria-00609399v1)). The rules above change what goes into `timestamp` and how `data` is split, not the envelope.
- **"The data type's problem" for parent and order** is the right split. The literature agrees that order and tree semantics are per type ([Weidner, part 1](https://mattweidner.com/2023/09/26/crdt-survey-1.html)). The only rule the envelope must enforce is that order and parent live on the child (rules 4 and 5).
- **No OT, no server reconciliation, no general CRDT library.** Nothing in browser sync needs text merging, and both of those need a central authority this design does not have ([Figma](https://www.figma.com/blog/how-figmas-multiplayer-technology-works/), [Weidner, server architectures](https://mattweidner.com/2024/06/04/server-architectures.html)).
